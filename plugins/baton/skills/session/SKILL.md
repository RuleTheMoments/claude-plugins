# 프로젝트 세션 핸드오프

긴 작업을 여러 세션과 compact에 걸쳐 진행해도 **사용자가 승인한 방향(목표·하지 않을 것·결정·계획)이 바뀌지 않게** 하는 것이 이 스킬의 목적이다. 다음 세션은 핸드오프 문서를 읽고(pull), 이 세션은 확인된 것만 남긴다(push). push할 때마다 문서 사본(체크포인트 `C0001`…)이 `<workdir>/.baton/`에 남는다.

**도우미** — 아래에서 `H`는 `python3 -I "${CLAUDE_SKILL_DIR}/../../scripts/handoff.py"`다. `--json`을 붙여 부르고 `status`로 판단한다. `message`는 사용자에게 그대로 전할 수 있는 한국어 문장이다.

**레지스트리 JSON과 `.baton/` 아래 파일은 직접 열거나 고치지 않는다.** 모든 기록은 `H`로 한다. 직접 고치면 잠금·검증·백업을 모두 건너뛴다.

모드는 사용자의 말에서 정한다.

| 사용자가 | 모드 |
|---|---|
| "…이어서 작업할 준비", "핸드오프 읽어줘", "지금까지 뭐 했는지", "resume" | **§1 이어받기** (읽기 전용) |
| "핸드오프 갱신", "지금까지 한 것 남겨줘", `save` | **§2 갱신** |
| "…를 등록해줘", `register`, 레지스트리에 없는 프로젝트 | **§3 등록** |
| "핸드오프 목록", "이어받을 수 있는 거", `list` | **§4 목록** |
| "이전 핸드오프", "C0003 보여줘", "언제 방향이 바뀌었나", `log` | **§5 이력** |

## §1 이어받기 (pull) — 아무것도 실행하지 않는다

1. **대상** — `H pull [이름] --json`.
   - `ok`이고 `by`가 `name`이 아니면 "실행 폴더 기준으로 `<키>`를 골랐다"고 한 줄 알린다.
   - `/baton:handon myapp 테스트부터 봐줘`처럼 이름 뒤에 요청이 붙어 오면 `unknown_project`에 후보가 하나(`myapp`) 나온다. 인자가 그 후보 이름으로 시작하면 `H pull <후보> --json`으로 다시 부르고, 나머지 말은 사용자의 요청으로 다룬다.
   - 그 밖의 `needs_target`·`unknown_project`면 `H list` 출력과 `candidates`를 보여 주고 묻는다. 후보가 없으면 등록할지 묻는다(§3). 추측해서 열지 않는다.
   - pull이 성공하면 이 세션이 그 프로젝트에 묶인다. 나중에 키 없이 push하면 여기에 쓴다.
2. **세션 이름** — 이번 턴에 훅 메시지 `[baton] 이 세션 이름을 '<키>'(으)로 붙였다`가 있고 키가 같으면 이미 됐다. 아니면 `H title <키>`. 출력 줄을 보고 보고 첫 줄에 쓴다.
3. **읽는다** — `handoff_doc`의 **고정층(`<!-- baton:fixed -->` 사이) 전체**를 먼저 읽는다. `plan_doc`이 있으면 그것도 전부 읽는다. 그다음 위험 → 진행 → 다음 행동 → 함정 순서로 읽는다. 다른 문서는 필요해질 때 읽는다.
   - 함정은 다시 실험하지 않고 믿는다. 이전 세션이 실제로 밟은 것이다. 다만 적힌 날짜·커밋 이후 관련 코드가 바뀌었거나, 사용자의 새 지시와 어긋나면 그쪽이 우선한다. 그 경우 "어긋난 것"에 쓴다.
4. **살아 있는 상태 — 읽기 전용으로만** 확인한다.
   - `git -C <workdir> status --short --branch`
   - pull 결과의 `latest_head`가 있고 `head`와 다르면 `git -C <workdir> log --oneline <latest_head>..HEAD`. 마지막 push 이후 들어온 커밋이다.
   - `latest_branch`와 `branch`가 다르면 어긋난 것이다. 커밋된 핸드오프 문서는 브랜치마다 다를 수 있다.
   - `notices`(예: 체크포인트 이력이 사라짐)와 `issues`도 어긋난 것이다.
   - **`setup`·`verify`는 여기서 실행하지 않는다.** 설치·빌드·테스트는 상태를 바꿀 수 있고, 먼저 돌리면 보고해야 할 어긋남을 덮는다.
5. **보고** — 전체를 다시 설명하지 않는다. 이 형태로 짧게:
   - **세션** — `<이름> · <세션 ID 앞 8자>` (대기 중이면 "다음 입력 때 적용")
   - **목표** — 고정층의 목표 한 줄
   - **마지막으로 증명된 단계** — 단계 ID와 그 증거(측정치·커밋)
   - **막힌 단계와 이유** — 있으면
   - **다음 행동 하나** — 계획 순서상 다음 단계. 앞 단계가 증거 없이 완료로 적혀 있으면 그 단계의 확인을 다음 행동으로 삼고 그렇다고 말한다
   - **어긋난 것** — 4의 결과. 없으면 이 줄을 생략
   - **근거** — 문서 경로, 최신 체크포인트 ID
   - **질문 하나** — "`setup`(명령 나열)으로 환경을 복원하고 `verify`(명령 나열)로 확인할까요, 아니면 바로 다음 행동을 시작할까요?"
6. **확인 필요에서 멈춘다** — 고정층이 비었거나(목표·계획이 없음), 작업 트리가 문서와 모순되면(브랜치가 다름, 기록된 커밋이 없음, 이력이 사라짐) 다음 행동을 제안하지 않는다. 무엇을 확인해야 하는지만 묻는다. 체크아웃·설치·재계획을 스스로 하지 않는다.
7. **사용자가 복원·검증을 원하면** — `cd <workdir>` 뒤 `setup`을 순서대로 실행한다. 오래 걸리는 것은 백그라운드로 돌리되, 끝나기 전에는 `verify`를 시작하지도 성공을 보고하지도 않는다. 그다음 `verify`를 돌리고 측정치로 보고한다.
8. 레지스트리 `warnings`에 미커밋 상태가 적혀 있고 실제로도 그렇다면 커밋할지 묻는다. 승인 없이 커밋하지 않는다.

## §2 갱신 (push)

1. **대상을 먼저 정한다** — 문서를 고치기 전에 정한다. `H current --json`의 `bound`가 이 세션이 묶인 프로젝트다.
   - 사용자가 키를 줬으면 `H resolve <키> --json`으로 확인한다. `match`가 있으면 그 키다. `bound`와 다르면 그렇다고 알린다.
   - 준 키가 등록되어 있지 않으면 문서를 고치기 전에 멈추고 묻는다: "`<키>`는 등록되지 않았다 — 이 폴더(`<workdir>`, 문서 `<경로>`)를 `<키>`로 등록할까요?" 승인하면 §3.
   - 키가 없고 `bound`가 있으면 그 키.
   - 둘 다 없으면 `H resolve --json`의 `candidates`(실행 폴더에 맞는 프로젝트)를 보여 주고, 그중 하나를 고르거나 새 이름을 정해 달라고 묻는다. 새 이름을 받으면 §3으로 등록한 뒤 이어서 한다.
   - **push 전에 `H pull`을 부르지 않는다.** pull은 이 세션의 기준을 최신으로 바꿔서, 그 사이 다른 세션이 한 push를 충돌로 잡지 못하게 만든다.
2. **진행 중인 것** — 돌고 있는 시험·빌드·에이전트는 멈추지 않는다. 문서에 "실행 중, 결과 미확인"으로 적는다. 완료도 실패도 아니다. 사용자가 세션을 끝낸다고 말했을 때만 정리한다(알리고 멈출지 기다릴지 묻기, `ps`로 남은 프로세스 확인, scratchpad에만 있는 산출물을 프로젝트의 gitignore된 곳으로 옮기기).
3. **사실** — 이번 세션에서 실제로 측정한 것만 측정치로 적는다("198개 통과, 2026-09-30 확인"). 이번 세션에서 확인하지 않은 숫자는 "마지막 확인 시점 …"으로 적는다.
4. **문서를 고친다** — 먼저 문서를 다시 읽는다. 바뀐 절만 Edit로 고친다. 통째로 Write하지 않는다(새 문서일 때만). compact를 거친 기억으로 문서 전체를 다시 쓰면, 요약에서 빠진 결정이 문서에서도 빠진다.
   - **변동층**(진행·위험·다음 행동·함정): 이번 세션에 확인된 것을 반영한다. 진행은 계획의 단계 ID마다 상태(완료·진행·막힘·보류)와 증거를 적는다. 함정은 이번 세션이 실제로 밟은 것과 낭비한 시간을 날짜·커밋과 함께 더한다. 해결된 함정은 지우지 않고 "해결됨 (날짜, 커밋)"으로 표시한다.
   - **고정층**(목표·하지 않을 것·결정·계획): 사용자가 이번 세션에서 명시적으로 승인한 변경만 고친다. 결정을 바꿀 때는 이전 결정을 지우지 않고 "<날짜> D3이 D1을 대체 — 이유"를 덧붙인다. 대화 요약이나 compact 요약을 근거로 고정층을 고치지 않는다.
5. **`H push <키> --json`**
   - `ok`·`unchanged`·`repaired` → 6으로.
   - `needs_approval` → `fixed_diff`를 코드블록으로 그대로 보여 주고 승인할지 묻는다. **사용자가 승인하기 전에는 `--approve-plan-change`를 붙이지 않는다.** 승인하면 그 플래그로 다시 실행한다. 거절하면 고정층을 직전 체크포인트대로 되돌린다(`H show <키> <parent>`로 원문을 보고 Edit) → 다시 push.
   - `conflict` → 다른 세션이 그 사이 저장했다. `diff`를 보여 주고, 그 세션의 기록이 사라지지 않게 문서에 합친다(Edit). 합친 뒤에만 `H pull <키> --json`으로 기준을 맞추고 다시 push한다.
   - `partial` → 사본은 저장됐고 색인만 못 썼다. `message`를 그대로 알리고 같은 명령을 다시 실행한다. `repaired`가 나오기 전에는 완료라고 하지 않는다.
   - `needs_target` → 1로 돌아간다. `error` → `message`를 그대로 알리고 멈춘다.
6. **요약 필드** — `H set <키> --one-line "…" --json`. 다음 세션이 이 한 줄만 읽고도 방향을 잡을 수 있게 쓴다. 위험이 바뀌었으면 `--warning`을 반복하거나 `--clear warnings`. 환경 명령이 바뀌었으면 `--setup`·`--verify`.
7. **보고** — 저장한 체크포인트 ID, 고정층 변경 여부, 핸드오프 문서가 git에서 미커밋인지. 5와 6이 모두 성공했을 때만 "이 세션을 닫아도 됩니다"라고 하고, 다음 세션의 첫 명령을 알려 준다: `cd <실행 폴더> && claude` → `/baton:handon <키>`. 승인 없이 커밋하지 않는다.

## §3 등록 (`register`)

**사용자가 등록을 요청했거나, 등록할지 물어 승인받았을 때만** 한다. 다른 모드에서 이름이 없다고 스스로 등록하지 않는다.

1. **키** — 사용자가 부르는 이름. 짧게, 공백·`/` 없이. `list`·`ls`·`목록`은 쓸 수 없다.
2. **workdir** — 저장소 루트(`git rev-parse --show-toplevel`). 절대 경로.
3. **핸드오프 문서** — 관례는 `docs/HANDOFF.md`. 없으면 아래 골격으로 만든다(Write). 고정층에는 **사용자와 정한 것만** 적는다. 정하지 않은 것은 "(사용자와 정할 것)"으로 비워 둔다. 그럴듯한 계획을 지어 넣지 않는다.
4. **계획 파일** — 이미 있으면(`.omc/plans/…`, `docs/PLAN.md` 등) `--plan-doc`으로 가리키고, 문서의 계획 절에는 "계획 파일 참조"라고만 쓴다. 계획 파일 전체가 고정층이 된다.
5. **setup / verify** — 추측하지 않는다. 저장소를 읽어 실제 명령을 찾는다(README, Makefile, package.json, scripts/).
6. `H register <키> --workdir <루트> [--doc <상대 경로>] [--plan-doc <상대 경로>] [--alias <별칭>]… [--one-line "…"] [--setup "<명령>"]… [--verify "<명령>"]… [--warning "…"]… --json`
   - `error`면 `message`대로 고친다(`key_exists`·`alias_conflict`면 다른 이름을 묻는다).
7. **첫 push** — §2의 5부터. 고정층이 있으면 `needs_approval`이 나온다. 처음 정하는 방향도 사용자가 승인한다. `<workdir>/.baton/`이 생기고, 그 안의 `.gitignore`가 자기 자신을 추적에서 뺀다.

### 핸드오프 문서 골격

기존 문서가 있으면 그 구조를 유지하되, 목표·하지 않을 것·결정·계획은 고정층 표시 안으로 옮긴다(옮기는 것도 고정층 변경이라 첫 push에서 승인받는다).

```markdown
# <프로젝트> 핸드오프

<!-- baton:fixed -->
## 목표
- (사용자와 정한 목표)

## 하지 않을 것
- (비목표·지켜야 할 제약)

## 결정
- D1 · 2026-11-19 · <결정> — 이유: … / 버린 대안: …

## 계획
- S1 <단계> — 완료 기준: …
- S2 <단계> (S1 뒤) — 완료 기준: …
<!-- /baton:fixed -->

## 위험
- 되돌릴 수 없거나 데이터를 잃는 것 (미커밋, 임시 런타임, 만료 임박)

## 진행
- S1 완료 — 증거: 호환성 시험 12/12 (2026-11-19, abc1234)
- S2 진행 — 저장 경로 구현 중, 시험 실행 중(결과 미확인)

## 다음 행동
- S2: … (무엇이 무엇을 막고 있는지)

## 함정
- 2026-11-19 · abc1234 · <밟은 것> — <피하는 법> (낭비 40분)

## 환경 복원
- 붙여넣어 실행할 수 있는 명령
```

## §4 목록 (`list`)

1. `H list`를 실행하고 출력을 **코드블록에 그대로** 보여준다. 요약하거나 재배열하지 마라.
2. 밑에 한두 줄만 덧붙인다.
   - "이 폴더의 프로젝트"가 하나면 `/baton:handon <키>`를 제안한다. 여럿이면 그 키들을 나열한다. 없으면 다른 폴더의 프로젝트도 키로 읽을 수 있지만 작업은 그 작업 폴더에서 띄운 세션에서 하는 편이 낫다고 알려준다.
   - ⚠ 점검이 있으면 무엇을 하면 풀리는지. `transcript_dir 불일치`는 그 프로젝트를 이어받은 세션에서 push하면 맞춰진다. 엔트리 형식 오류는 `H set`으로 고친다.

## §5 이력 (`log`)

- `H log <키>` — 체크포인트마다 시각, 세션, 원 대화(트랜스크립트)가 남아 있는지, 고정층 변경 여부. 출력을 코드블록으로 보여준다.
- `H show <키> <ID>` — 그때의 문서 원문. `H show <키> <ID> --against <ID2>` — 두 시점의 diff.
- "언제 방향이 바뀌었나" → `고정층 변경` 표시가 있는 체크포인트마다 직전 체크포인트와의 diff를 보여준다.
- 원 대화가 필요하면 그 체크포인트의 `session_id`로 `claude --resume <id>`를 안내한다. 어느 폴더에서나 되지만, 그 대화의 명령은 새로 띄운 폴더에서 실행되므로 원래 실행 폴더에서 띄우라고 함께 알린다. 트랜스크립트가 없으면(`원 대화 없음`) 남은 것은 문서 사본뿐이라고 말한다. 사본에도 없는 내용을 복원했다고 하지 않는다.

## 하지 말 것

- 레지스트리 JSON이나 `.baton/` 파일을 직접 열거나 고치지 마라
- 사용자 승인 없이 `--approve-plan-change`를 붙이지 마라
- 이어받기에서 `setup`·`verify`를 묻지 않고 실행하지 마라
- push 전에 pull로 기준을 덮어쓰지 마라 — 충돌을 합친 뒤에만 pull한다
- 레지스트리에 없는 이름을 추측해서 아무 프로젝트를 열지 마라
- 확인하지 않은 숫자를 현재 상태로 적지 마라
- 승인 없이 커밋하지 마라
- 프로젝트가 명시적으로 금지한 경로에 쓰지 마라 (그 프로젝트의 `CLAUDE.md`/`AGENTS.md`를 먼저 읽는다)
